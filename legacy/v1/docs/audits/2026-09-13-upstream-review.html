05 / Background workers: capability ≠ isolation

What our code already does

spawn_background and the manual background command create metadata, preserve the requesting message/channel, schedule a strongly referenced asyncio.create_task, and return without awaiting the whole worker. Defaults allow two active jobs globally and one per user. A full cap refuses extra work; there is no durable backlog waiting for admission. These are source defaults, not an inspection of root’s live configuration.

Manual bg <goal>, jobs and owner/admin cancellation already exist. However, model-facing spawning is classified as a result tool, not an enforced turn-ending operation: “acknowledge only” is an instruction, and same-batch siblings or follow-up work may still run. The job uses the same bot, event loop and tool environment. A separate coroutine is neither another process nor a security sandbox.

Admission and spawn · manual commands · result/ending categories.

Our extracted persona needs an explicit worker setup decision

In external-prompt mode, our bot removes the legacy _control['base_personality'] key, while the worker still reads that key directly. Its system prompt can therefore omit the configured personality. Upstream already prefers the bot’s _get_personality() accessor. If workers should share Curie’s configured persona, use our existing accessor and a synthetic prompt-sentinel test; if workers should have a separate task role, make that deliberate rather than inheriting an accidentally empty legacy field. No private prompt contents were inspected, and no upstream persona should be transplanted.

our worker’s legacy read · external-prompt key removal · our accessor · upstream accessor usage.

What upstream adds—and what it does not

  • Worker model override: bg_model/BG_MODEL, default string gemini-3.8-flash-high. It still calls bot._generate_response(model=...), borrowing main-provider endpoint/auth and its fallback behavior. This is not the requested separate endpoint system, and the alias is not a verified available model.
  • Useful selective fixes: setup/pre-start cancellation bookkeeping; a clean-finish condition so time/step exhaustion is not “done”; filtering worker send_message and recursive spawn; task-appropriate results with a URL only when one exists. Tool filtering alone does not remove all side effects.
  • Do not import the final-reply rewrite: upstream spends a main-route LLM call to write a short completion message, undermining endpoint isolation and adding cost. Its final send failure can still be recorded as done. Preserve our already-fixed private incidents and delivery-failure handling.
  • Not present: independently leased provider clients, per-profile keys/options, versioned hot swap, hard foreground capacity reservation or resumable side-effecting workers.

worker model selection · main-provider call · fallback path · completion rewrite · completion/delivery.

Why “background” still competes with the foreground

Our workers acquire the shared chat FairSemaphore. Priority orders waiters; it does not preempt existing holders or reserve a slot. With two worker calls and a shared capacity of two, Curie’s next live turn waits even if it has higher priority. Independent HTTP endpoints alone do not fix that scheduling boundary.

Use a worker-only admission pool plus explicit foreground headroom, per-profile limits, deadlines and shared-resource controls. Do not inline a worker into the main turn when admission fails. A second endpoint also cannot guarantee availability if it reaches the same saturated GPU or if tools block the shared event loop.

worker acquisition · waiter priority.

Persistence: preserve the configuration first, not a false promise of resumable work

Both versions persist job metadata and mark interrupted jobs cancelled at startup. That is not continuation from the previous tool step. Upstream’s separate foreground request journal also does not prove restart recovery: later code deliberately abandons pre-boot inbound requests.

Version one should retain named profiles/default selection across restart and explicitly cancel interrupted jobs. Restart-proof execution requires checkpoints, idempotency, ownership leases and delivery reconciliation. It is a separate high-risk feature, especially for paid generation, filesystem writes and Discord side effects.

our restore behavior · upstream pre-boot abandonment.

06 / The profile and secret design I recommend

Proposal · commands and schema do not exist yet

Named profiles, not fragile list positions

Keep N profiles keyed by stable names such as builder, research and review. Each explicitly owns its transport, endpoint, model, non-secret request parameters and secret reference. Persist the selected default separately. Numeric menu positions can be display conveniences, never identities that silently change when reordered.

No borrowing the main route

Worker generation, retries, fallbacks and completion summarization must stay within its selected profile. Missing key, invalid endpoint, rejected parameter or unavailable provider means an explicit refusal/failure—not “helpfully” using Curie’s main model.

Illustrative non-secret metadata

{
  "schema_version": 1,
  "selected_profile": "builder",
  "profiles": {
    "builder": {
      "revision": 3,
      "transport": "openai-compatible",
      "base_url": "https://api.example.invalid/v1",
      "secret_ref": "provider-build",
      "model": "vendor/model",
      "request_params": {"reasoning": {"effort": 75}}
    }
  }
}

Synthetic example, not a configuration to install. The reasoning shape is OpenRouter-style, not a universal provider schema. Preserve JSON scalar types exactly: integer 75 stays integer 75. No rounding, enum substitution, dropped fields or “retry with a friendlier value.” Initially support the already-understood OpenAI-compatible transport; arbitrary URLs do not make native Anthropic/Gemini/Azure protocols interchangeable.

Hot swap means a new admission snapshot

  1. Validate a metadata update without mutating the active client or main configuration. Reject conflicting reserved fields such as messages, tool ownership, auth headers or routing overrides instead of silently overriding them.
  2. Atomically publish profile revision V+1 and persist the selected default. Use private identity-owned storage, a lock and replace-on-success semantics; malformed updates do not destroy the prior valid configuration.
  3. A newly admitted job records an immutable profile revision, exact parameters and an opaque private credential-generation reference. Resolve secret_ref to that generation at admission, not to a mutable “latest key” on every request. Running and already-admitted jobs retain V and the same credential generation.
  4. Rotation writes new private key material first, then publishes a new profile/credential revision for new admissions; no key value enters job metadata. Lease clients by profile plus credential generation, draining old users before closing old sessions. Emergency revocation explicitly cancels/fails closed. It is not automatic rerouting.

Keys: private references, never Discord input

  • Store provider keys in private service-owned files/mounts, outside prompts, images, Git, sites and tool-readable workspaces. Owner-only permissions; private parent directories. No keys in command arguments, logs, dashboard public assets, job metadata or exports.
  • Expose only secret_ref, configured/missing status and allowed endpoint origins in administrative metadata. Bind a key reference to approved origins so an endpoint edit cannot silently forward an existing key to a new host. Reject provider redirects in version one. Stripping auth alone is insufficient: a 307/308 can replay the private prompt/tool POST body to a different recipient. Use the configured canonical HTTPS endpoint, with private-local HTTP only by explicit operator policy; never follow a downgrade or silently select a different recipient.
  • Register newly resolved/rotated credentials with producer-side redaction before transport use, preserving protection for late events from old leases. The standalone console still must not load the secret store.
  • Add/rotate the actual key through a private local operator workflow. Do not accept raw keys in a Discord command—even an admin DM is stored chat and is the wrong secret store.
  • Use authenticated admin commands for non-secret profile selection/model/effort/parameter edits, with fenced, balanced reports. Non-admins must not create routes, enumerate secrets or pick an unrestricted expensive profile.
  • Persist metadata/default selection and secret references across restarts. Test deletion/rotation/missing keys without falling back to main. Do not read the secret store merely to make a console prettier.
PROPOSED COMMAND SHAPE — configured prefix applies
!worker profiles
!worker use builder
!worker model builder vendor/model
!worker params builder {"reasoning":{"effort":75}}
!worker status

Actual keys: private operator workflow, not a chat command.

Tool-owned services such as image generation, embeddings and search retain their own explicit routes/capability policies. A worker’s chat endpoint is not a blanket replacement for every tool’s external service.

Required synthetic acceptance before enabling independent workers
  • Two fake endpoints receive only their own model, parameters and key; the main route is a boobytrap that must never be called by worker generation or completion.
  • Switch default or rotate a key while job A waits in HTTP: A finishes on its original profile/credential generation; new job B uses the new revision. Test removal/emergency revocation separately. Old sessions close only after their final lease.
  • Restart reloads profiles/default; malformed files and unknown secret references fail visibly without overwriting valid configuration or borrowing main.
  • Every integer1–100 is parametrically tested unchanged, not a new set of example presets. Nested JSON types also survive; provider rejection is reported without silent substitution.
  • A→B307/308 redirects fail explicitly: B receives neither key nor body, and the main route is never a fallback.
  • Wrong-origin endpoint changes, unauthorized commands and recursive worker spawning are refused. Keys never enter model messages, status posts, console fields or incident exports.
  • Occupied worker capacity leaves a foreground request able to start; deadlines/cancellation release all slots and clients.

08 / Restore useful live updates, not raw-output leakage

First: deterministic worker status

One owned status message per job. Send once, edit on meaningful changes, throttle/coalesce updates, and perform one terminal handoff. Show job/profile/model, actual phase, elapsed time and step budget. A counter such as “step7 / limit80” is not 8.75% task completion.

Then: opt-in shell preview

Keep existing bounded stdout/stderr draining, timeout and process-group cleanup. Add a separate publisher that receives sanitized bounded output/status; never reactivate old unbounded buffers or assume the dormant helper is wired up.

These status edits do not need periodic paid calls to the main model. A local heartbeat reads already-known process/job state. Task-specific “45/80 records” is useful when a script actually reports that quantity; invented progress percentages are not.

  • Key ownership by job/request/channel/message, not a bot-global “current progress” variable. Update the returned Message.edit object; tests must model the SDK returning a new object.
  • Handle 429 retry timing, forbidden/deleted messages, cancellation, terminal-edit races and partial delivery. Failed progress presentation must not restart generation or duplicate the final result.
  • Treat command text, stdout and error bodies as potentially secret-bearing. Default public Discord updates should contain safe metadata, not raw shell output, private prompts or internal reasoning. Even an explicitly enabled preview remains redacted and bounded.
  • Keep console output and Discord output separate sinks. Console expansion is not authorization to publish private evidence into a thread.
  • Preserve Curie’s intentional count-only worker step posts and private incidents until a new, explicit output policy replaces them.

our bounded subprocess/cancellation path · active static callback · our count-only progress contract.

09 / Narrow safety findings—not a rewrite invitation

These are specific, evidenced boundaries to account for. Except for the explicitly approved site hotfix, they are not patched by this logging/report work.

J1 / Cross-turn worker transcript contamination

High-risk when workers overlap other tool dispatches; source-proven interleaving, not a production exploitation claim. A dispatcher writes bot-global _last_native_followup_messages. The worker awaits a Discord progress post before reading that global field. Another foreground/worker dispatch can replace it during the await, and the first worker then sends the other turn’s tool followups in its next model request. Upstream retains the same pattern.

  1. A dispatch publishes A’s followups.
  2. A waits on thread.send.
  3. B dispatch replaces the bot-global followups.
  4. A resumes, appends B’s followups and uses them in its next request.

Require invocation-owned dispatch results/transcripts before expanding worker concurrency. Our already-repaired response-owned ProviderResult.tool_calls is a different boundary; do not claim that repair covers this handoff.

our await/read ordering · global publication · upstream equivalent.

J2 / Non-admin DM job listings can cross conversation boundaries

Source-confirmed conditional access flaw. The DM command passes an empty guild ID; the list method interprets that as no guild filter. An eligible non-admin can receive the latest ten job summaries across conversations: ID, status, owner mention, first 60 normalized goal characters and time—not full results, credentials or complete context.

The prefix-command path runs before reply_dms/normal conversation gates. Reachability still requires a user able to DM, not ignored/blacklisted, with the command not disabled. No live configuration or exploitation was checked. Upstream adds an owner filter, but its manual/tool-spawn DM sentinels differ: adapt with tests, do not cherry-pick blindly.

The boundary is broader than DMs: our guild listing filters only by guild, and job <id> admits a same-guild requester without checking visibility of the originating channel/private thread. That direct response contains up to 200 goal characters. Upstream’s direct lookup retains the same-guild-only gate and also exposes progress. A shared guild is not permission to read every job in it. Apply origin visibility/ownership rules to both listing and direct lookup, and keep privileged cross-context inspection out of unrelated public channels.

entry ordering · command authorization · unfiltered blank-guild listing · upstream owner filter · our direct lookup · upstream direct lookup.

A1 / Revoked dashboard administrators keep existing OAuth sessions until expiry

Our _discord_token_authed checks cached existence/expiry, not the current admin set. Login checks authorization, but a previously authorized user’s existing token remains accepted after removal until expiry or API-process restart; a bot-only restart is not equivalent. This matters if an admin is revoked and can still reach the API; it does not establish an active compromise in a solo-owner deployment.

Upstream rechecks current authorization and removes invalid cached tokens. A repair must cover both protected API requests and discord_auth_verify, which has its own cached-expiry check and sits under the OAuth middleware exemption. This is a small auth-boundary candidate, not a reason to import the dashboard/install redesign. Test login → revoke → protected request and verify request, including the separate immutable owner/environment allowlist semantics.

our cached check · administrative acceptance · upstream revocation check · our OAuth verification.

S1 / Site read-loop identity reuse: the one approved hotfix

Our old counter map used id(message) without retaining/checking the owner. Recycled Python object IDs could make a fresh message inherit stale idle/test counts and refuse its first valid site read. This was not merely hypothetical: the initial logging candidate’s full suite hit the existing slotted-message regression.

Root explicitly approved a separate fix. Commit e1a6222 retains/checks the exact message object while preserving the128-entry bound and same-turn guards, selectively adapting upstream0744abc. Two deterministic tests fail on the old code; the hotfix-only full isolated suite passes3504 tests. Test state was not cleared to conceal the failure.

Tradeoff: up to128 message owners are retained by this existing bounded cache. This is a bound on entries/owners, not a claim of constant exact byte usage.

Additional lifecycle prerequisites for wider worker use: distinguish time/step exhaustion from clean completion, capture pre-start cancellation/setup failure, preserve result-versus-delivery status, and test native-history budgets. Upstream has useful pieces but does not solve every one of these boundaries.

11 / Console: pretty for root, boring for parsers

The key separation is source evidence → normalized events → presentation. Color, folding and keyboard controls belong in the last layer. They must not replace the machine evidence with terminal paint or silently rewrite producer behavior.

Docker raw history (unchanged, private, finite retention)
             │
       EventParser + recognizers + redaction
             ├── JSONL: one normalized record per received line
             └── Console: timestamps / scope / fold / replay / color

Future worker events ── new recognizer / renderer, not a new monolith

Implemented foundation

Commit 1ca2690 adds explicit curie logs --format jsonl, schema-v1 linewise events, separate producer/Docker/observed time facts, and complete retained image prompt/request details after redaction. Selected timestamps are ISO-shaped without inventing UTC for naive producer timestamps. Original source spelling remains available. Default legacy plain/coalesced output and the Docker backend are unchanged in that commit.

Commit d45f8bb adds explicit unparsed diagnostics (parse_error), safe deep/malformed-JSON fallback, immutable evidence snapshots and per-service traceback grouping. Retained history is bounded by 500 line-records and 2MiB of serialized ASCII JSONL evidence—not total process RSS or transient input size. Whole events/groups are evicted, with oversized/partial-tail markers and no silent clipping of admitted prompts. The full isolated suite passes 3,589 tests for that slice.

Validated interactive implementation

  • Timestamped, colorized TTY output; no-color support; non-TTY output stays noninteractive and machine-friendly.
  • Fold/expand, local verbosity, scope filters, tool/provider depth, recent/error replay, selected-evidence navigation and bounded history.
  • Events positively identified as subagent activity stay collapsed in live display, even when other scopes expand. Explicit selected-event inspection can reveal retained evidence; this does not publish it to Discord. Existing provider/tool descendants without job correlation remain ordinary/unattributed records: timing or prompt words cannot establish ownership. The future worker integration must propagate explicit job context before claiming that all worker logging is attributed and collapsed.
  • Whole-event/group eviction instead of silently clipping prompt fields. Oversized/not-retained and incomplete traceback evidence must be labelled and traceable to original Docker logs.
  • Terminal-control neutralization, malformed/deep-JSON recovery, signal/TTY restoration and follower-only shutdown. Ctrl-C must not stop the bot.

logs --format auto|console|plain|jsonl: auto/console require capable input and output TTYs; otherwise they use legacy plain output. NO_COLOR disables colors, not controls. JSONL is an export stream, not an automatically created archive. The TTY reader separately marks and discards physical input records over 2MiB; that cap does not apply to JSONL mode. Compact live timestamps use P producer, P? unspecified producer timezone, D Docker or O collection time; full dates/precision/provenance remain in selected evidence and JSONL.

The skill is guidance, not a privilege sandbox. It distinguishes source hypotheses, synthetic regressions and live observations. The implementing agent still owns fixes and isolated test execution.

Rollback contracts for the proposed worker/thread features
  • Workers: stop admission through both the manual background command and model tool; then drain or explicitly cancel existing leases/jobs. Preserve profile versions, current private secret bindings and diagnostic metadata. Never use a blind old-image rollback that silently re-enables legacy main-route workers; verify both entry points remain disabled under the selected rollback version before restoring service.
  • Profiles: select a prior valid metadata revision only if its endpoint/key generation is still authorized. A revoked or removed key is not restored merely because old metadata references it. Do not close clients still leased by running work.
  • Threads: disable new thread tools/automatic routing without erasing briefs, RAG or real Discord threads. Preserve already-created thread IDs for later reconciliation; do not “rollback” by deleting conversations.
  • Progress: disable the publisher and retain the normal result-delivery path. Clear/finalize owned UI state without replaying tools, regenerating outputs or duplicating the completion message.

Cut these first if the change budget gets uncomfortable

  • Durable resumable workers / separate worker service: defer. Keep explicit restart cancellation; do not replay side effects casually.
  • Arbitrary provider protocols: defer native adapters beyond the verified OpenAI-compatible path. Profiles are still useful with several compatible providers.
  • Automatic thread creation/archival everywhere: defer. Start with explicit operations and a dedicated guild task space.
  • Raw live stdout in public channels: defer. Safe job phase/counter updates deliver much of the value with less leakage and rate-limit risk.
  • Jina fallback, host-file additions, broad persistence/CI work: independent backlog, not prerequisites for worker routing.

Do not cut: secret isolation, invocation-owned transcripts, authorization, no-main fallback, foreground capacity tests, truthful completion and rollback. Those are the foundation, not optional polish.
