## Push-backs and corrections before implementation

1. **C-01: no tool execution from a `length`-terminated response merely because JSON parses.** Syntactic completeness is not semantic completion. If root permits partial answers, render genuine answer content as explicitly incomplete, outside native/text-tool recovery and dispatch. Never promote private reasoning into it. Keeping failures terminal remains defensible; the generic public error and missing telemetry are separate issues.
2. **C-33: the service-name rejection has NOT already passed the redactor.** `append_events.py:103–107` replaces the original line before `parse`; the redactor runs later in `content` at line 83. This differs from the structure-depth check, which follows redaction. Blind per-record recovery for both can skip a private-key/config opening marker and expose subsequent lines. Distinguish parsing rejection from lost redaction continuity. Any recovery needs demonstrated state preservation, not a cleared flag. Trailing-usage draining similarly needs a bounded deadline, not an indefinite wait for `[DONE]`.
3. **C-32 visibility and anchor precision:** individual omission events are filtered out, but `append.py:133–134` already emits an out-of-band continuity-failure notice; the failure is not wholly silent. Several cited anchors are wrong (`scopes.py:373`, `append_state.py:237`, `safety.py:263` are beyond current file lengths); the corrected relevant anchors are above. The 33-bracket mechanism is source-confirmed. Other injection/framing examples still need exact fixtures; a 100-character limit is not a 100-byte limit.
4. **C-02: avoid universal wording and a false guarantee.** A near-32k result leaves insufficient room for one ~4k older compacted result, but smaller prior results can survive; not every large result erases all history. A multi-tool batch can contain several near-32k results. Excluding the newest group or changing 36k to ~41k is not a general bounded-context solution. Define retention/total-size invariants across whole batches and public arguments.
5. **C-23: environment filtering is defense in depth, not secret isolation.** A same-UID shell can still read the bot-readable configuration and state; `docs/ARCHITECTURE.md:47–49` already states that filesystem exposure. Whitelisting the human does not stop injected external content acting inside an authorized human's turn. Do not sell a filtered environment as solving that risk.
6. **C-14: no new evidence of an upstream reasoning/content mix-up.** The audit's hypothetical DeepSeek quirk does not justify resurrecting promotion. If recovery is wanted, it is a separately budgeted retry policy, not reinterpretation of private reasoning as an answer.
7. **The recommended “hygiene, no runtime effect” slice is mislabeled.** Media retention, tool-result memory, image behavior, cancellation and smoke turn settlement all change runtime behavior. They need focused acceptance and review. I would not bundle them under documentation cleanup.
8. **Process evidence needs precision.** Post-rollout report mtimes or a short commit-to-rollout gap do not prove there was no pre-deploy review/QA; frozen snapshots can be tested before committing. Existing receipts do not establish whole-app acceptance either. Bytecode presence alone is not proof of application import. The actionable problems are incomplete decision/debt ledgers, evolving acceptance and too much reactive live iteration.
9. **P-03: no green-by-suppression.** Classify each baseline failure as a product defect, obsolete expectation or unsafe live test, with an owner and disposition. Do not add `xfail` merely to publish a zero-failure headline. The existing no-new-tests rule remains in force unless root explicitly changes it.
10. **C-03/C-28 and compatibility:** changing the preserved `prompt` handler or adding a removed `hd_image` alias is not automatically authorized by a finding. Revisit the former explicitly if desired; the latter needs evidence and a compatibility decision, not an automatic reversal of clean-cut removal.
