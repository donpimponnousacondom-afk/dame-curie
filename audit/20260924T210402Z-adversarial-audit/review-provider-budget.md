## Open blocker — C-06 malformed competing cap on alternate-first route

Foreground `n` enforcement now meets the selected *single-completion* source policy: `providers.py:1855-1860,2411-2414` rejects an **explicit** `n` unless its type is exactly `int` and its value is `1`, before session/attempt/reservation/POST. The final payload guard at `:2575-2582` repeats this check each attempt, before reserve; absent `n` remains absent. Nonforeground bypasses these guards, preserving configured extras. Existing `tests/test_provider_error_reporting.py:716-757` checks `n=2` rejection without POST/attempt, `n=1` acceptance and unchanged nonforeground `n=2`. No multi-choice feature is added.

**One source-backed policy hole remains.** `providers.py:1863-1872` rejects malformed `max_completion_tokens`/`max_output_tokens` and clamps valid positive integers to `data["max_tokens"]`; `:2578-2582` runs it before and after foreground reservation on the **selected attempt payload**. But the generate-entry guard checks only `n` (`:2411-2414`), not configured alternate caps. Primary `self.extra_body` is copied only for a primary endpoint (`:2184-2187`), whereas `_attempt_endpoint` (`:2041-2056,2068-2092`) can choose vision/fallback first for media, `prefer_fallback=True`, or primary cooldown. With primary `OPENAI_EXTRA_BODY={"max_completion_tokens":0}` and a configured fallback selected first, that fallback's payload has no alias: it can reserve and POST at `:2580,2620` before the malformed configured cap is checked on any later primary attempt; if fallback succeeds, the malformed value is never rejected. That contradicts the coordinator-selected **terminal before any reservation/paid fallback/POST** malformed-cap policy, even though a primary attempt itself rejects it before its own reserve. Minimal fix: validate present recognized alias **values in `self.extra_body` at foreground generation entry**, before endpoint/session work (positive `int`, excluding `bool`); keep per-attempt pre/post-reserve clamp unchanged. Do not apply the foreground restriction to nonforeground calls or remove unrelated extras, endpoints or keys.

The otherwise correct per-attempt cap behavior is: values above admitted `max_tokens` are lowered; configured lower positive caps stay lower; after `turn.reserve` reduces wire `max_tokens`, both aliases are clamped again before POST (`providers.py:2578-2582`). Payload rebuilding on retries (`:2536-2558`) and learned output-cap adjustments (`:2860-2892,2927-2945`) re-enter those guards. No paid retry occurs *after* a selected primary payload fails the pre-reserve validation, because its `ValueError` is outside the request `try` at `:2619`. Provider-specific precedence between `max_tokens` and competing cap fields remains unknown; do not call it a live/provider-proven bypass. `tests/test_provider_error_reporting.py:724-740` checks an over-cap alias, a lower cap and an unrelated extra on a normal primary attempt; it does **not** test malformed alias types/zero, alternate-first routing, or a second clamp after a reservation smaller than requested. Extend that same existing case with a fallback-first malformed alternate cap and `turn.attempts`/request count still zero; add synthetic lower-remaining and malformed `bool`/zero cases, no new test functions.
