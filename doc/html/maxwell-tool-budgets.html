01 / Executive answer

The counter works. The overall budget does not.

The model chooses whether to ask for another tool. The application must decide whether that work is still allowed.

The observed behavior is not evidence of an infinite loop inside one normal chat turn. The foreground loop has a finite range(max_iters). But the baseline permits 50 tool batches, each containing multiple calls. Discord has a one-hour soft time budget; Telegram lacks that loop deadline. The code does not assess whether another successful search adds useful information.

What is already enforced

  • Finite foreground and detached-job iteration ranges.
  • Some per-request timeouts, concurrency limits, and tool-specific permissions.
  • Narrow site-read-loop and acknowledgment-only protections in foreground chat.
  • A failure circuit breaker—not a successful-repetition detector.

What is missing or inconsistent

  • A cumulative tool-call and per-tool budget.
  • An end-to-end deadline shared by queues, retries, tools and finalization.
  • A reliable final answer and honest exhaustion status.
  • Budget/policy propagation through pre-tools, delegation and other execution paths.

Practical impact: long research runs, repeated searches, unexpectedly high model/API work, unanswered requests at the cap, and background work incorrectly presented as complete. Cross-platform write tools make automatic retries a correctness issue, not only a cost issue.

Grounding order: current source and tests → current configuration templates and docs → historical audits as leads only. Initial findings were at 8dfde35; 57d5b8c adds the reference HTML guide, not a runtime fix. See source map.

03 / Confirmed findings

Where the boundaries fail

F1 · Rounds are not calls; success is not progress

High · workload controlReproduced

The native dispatcher normalizes the full model batch, partitions it, and runs nonterminal tools with asyncio.gather. It does not reserve a total-call allowance before launching them. web_search has no turn-local query deduplication or cumulative search limit. Successful searches, including empty-result searches, can keep requesting follow-up generations.

Configured: 2 tool rounds
Round 1: 4 × web_search → all four execute
Round 2: 4 × web_search → all four execute
Total:   8 tool calls, not 2

The failure breaker opens after five failures in its 60-second window and recovers after 30 seconds; success resets its failure history. It does not stop five successful calls returning the same information.

F2 · Time budgets are soft, absent, or restarted

High · latency and costDiscord reproduced

  • Discord: checks time before dispatch, not before the following model request. A slow batch can exceed the deadline and still trigger another full generation.
  • Telegram: has the same round cap but no loop-wide time-budget check.
  • Jobs: remaining time is calculated before waiting for a model slot and reused afterward. Dispatch and delivery have no job-remaining-time wrapper.
  • Provider: each HTTP retry can still receive the original timeout. Since 5e9b5be, tool-protocol correction shares the fixed attempt budget instead of starting a second one; a shared end-to-end deadline remains missing.
  • Search: the 30-second wait ends before inline RAG persistence. Cancelling that wait does not kill an already-running executor thread.

F3 · The last round can discard the answer's next action

High · user-visible correctnessReproduced on both chat loops

After the final allowed dispatch, foreground chat still asks the model to continue with tools enabled. If the model returns tool calls, there is no next dispatch to run them. No explicit exhausted state or tools-disabled wrap-up follows. Empty assistant text can therefore leave the user with no final answer.

Background jobs have a related status bug: once any generation succeeded, exhaustion or a later failure can end with status done and “Done — details are in the thread.” That is not proof that the requested task finished.

F4 · A background job can ignore a successful terminal tool

High · repeated deliveryReproduced

The job loop recognizes an ending-only batch only if resp_text.strip() is also nonempty. Native send_message often has empty assistant content: the answer is in the tool arguments and the delivery result. A successful terminal-only message can therefore be followed by another model round and another message.

  each response = native send_message + empty assistant content
  each tool result = successful delivery of a completed answer
Observed: 2 generations, 2 sends, final_text = "", succeeded = True

Use explicit execution outcomes and ending-tool semantics, not the presence of leftover assistant text. Preserve the foreground distinction between a completed answer, an acknowledgment, and a mixed batch with results still needing interpretation.

F5 · Pre-tools and delegated jobs escape the parent accounting scope

High · policy propagationSource-confirmed

Discord's automatic current-information search executes before initial generation and before the foreground tool deadline starts. It bypasses the counted dispatcher. A foreground cap of zero does not stop this search while tools remain enabled.

Detached jobs deliberately use extended independent budgets. More seriously, autonomy's direct research deny list does not include spawn_background. Its synthetic request can create a job whose worker rebuilds the normal bot tool catalog, removing only recursive spawn_background. The parent's research prohibition and six-action tick allowance do not follow that child.

This is a source-path policy escape, not evidence that production used it and not an infinite single job. Concurrent-job limits constrain active jobs, not total work created over many ticks.

F6 · X write retries can multiply a side effect

High · cross-platform correctnessSource-confirmed, no live write test

X has its own backend layer below tools. XClient._write tries another configured writer after XError, and a transport timeout can become that error. If the first backend accepted a post but its response was lost, falling through may create a second post. post() releases its hourly reservation on exceptions, including ambiguous outcomes. like, repost and delete do not consume that post budget.

A shared round limit alone cannot fix this. Separate safe read retries from ambiguous write outcomes. Do not replay an external write until it is known not to have committed or can be reconciled with an idempotency mechanism.

Email: partial success is not a safe full retry

IMAP polling defaults to 120 s (runtime 30–3,600), fetches up to eight UID entries per tick and bounds snippets. It does not call a model itself. Both polling IMAP and tool IMAP lack explicit connection/whole-operation deadlines in the inspected paths, so a hung read can prevent the failure-backoff logic from being reached.

Sending has a distinct duplicate-delivery risk: a send can accept some recipients and refuse others, then return a generic error. A retry of the original recipient list can resend to people already accepted. Each new invocation generates a new Message-ID, the recipient list is not capped here, and SMTP's 60-second I/O timeout is not a whole multi-recipient deadline. Cancelling the await does not stop a running SMTP thread. The inspected path has no application hourly send/recipient allowance or reconciliation ledger.

Report accepted, refused and uncertain recipients separately. Retain charges for started/uncertain delivery; do not treat a generic tool error as proof that nothing was sent. Inbox action acknowledgment and external action success also need separate states.

Voice: no tool loop, but independent work still needs boundaries

Canonical merged controls—not the smaller local fallback literals—give voice a 45-second AI timeout, 1,000 output tokens, 2,000 response characters, 18-second utterance segmentation, 0.8-second pause and 0.55-second minimum utterance. ASR and some Riva/gTTS executor paths lack explicit deadlines. Newest-utterance cancellation prevents stale playback through generation checks, but cannot retract remote work already running in those threads. Preserve this newest-wins behavior while bounding worker capacity and ASR/TTS cost. Attached audio in text chat follows the ordinary media/chat path; it is not the same workflow as live VC.

Plugins and manual/API roots: define the supported boundary

Model-invoked plugin tools pass normal per-user/platform policy and concurrency checks. In contrast, plugin setup receives the full bot; ctx.tool returns a raw tool; events and recurring jobs run callbacks directly. A plugin job repeats at an interval with a five-second floor, not a finite lifetime round cap. Current per-user plugin disable state does not stop all registered recurring jobs.

Message events are dispatched before inbound deduplication, so a repeated gateway event can repeat plugin side effects even when normal reply handling discards it. Plugin reload cancels old jobs without waiting before starting replacements; orderly teardown does cancel and await jobs. In-flight detached event callbacks need ownership too. These are infrastructure paths, not a claim that the bundled tool-only checkers plugin is running such jobs.

Manual ,bg creates jobs directly even if the spawn tool is disabled; the job's model dispatcher still honors the global tools switch. Manual/API autonomy ticks can run while the scheduler is disabled. The API command queue is authenticated and allowlisted, with shell explicitly forbidden—not an unauthenticated arbitrary-tool endpoint. Deleting a queued command is not cancellation of an already-loaded consumer snapshot.

Cancellation is a request, not settlement

Live ,stop cancels the active reply/queue; detached jobs require their own stop/cancel path. The job manager marks a job cancelled immediately after Task.cancel, and status-based capacity may be reused before the task has settled. Runtime cleanup also precedes final delivery in the worker. Do not equate a UI status or freed slot with proof that all old side effects stopped.

Autonomy stop owns its scheduler task, not every separately invoked tick or delegated child. Shell already has process/process-group cleanup on timeout/cancellation; this report does not claim shell cancellation is absent. The remaining shared requirement is settlement tracking, owned descendants and honest uncertain-result handling for work that cannot be recalled.

05 / Recommended implementation contract

Budget the operation, not the loop variable

Proposal · not current APIs

Introduce a small shared execution-budget component at the orchestration/dispatch boundary. Keep platform adapters and working tool implementations intact where possible. This is not a request to rewrite the bot or merge every scheduler into one giant loop.

1 · AdmitResolve origin, permissions, profile, hard deadline and remaining allowances.
2 · GatherPre-tools and media work draw from the same operation budget.
3 · GenerateQueue wait, provider calls and retries use remaining time and attempt limits.
4 · ReserveNormalize, authorize and reserve permitted calls before any parallel launch.
5 · ExecuteBound each call; record success, failure, cancellation or uncertain side effect.
6 · DecideContinue only if useful work and budget remain. Terminal outcomes stop.
7 · FinalizeUse reserved time for at most one tools-disabled summary—or deterministic partial output.
8 · FinishPersist and report a truthful outcome. No implicit budget reset.

A. Define separate units and counters

  • Tool rounds: batches admitted to execution; preserve the current foreground meaning during migration.
  • Tool calls: individual admitted invocations, with total and per-tool caps. One batch of 20 searches must consume 20 call reservations before it starts.
  • Model requests and HTTP attempts: distinguish model decisions from transport retries. Count the initial request, follow-ups, protocol fallback and final summary.
  • Elapsed time: one monotonic operation deadline, including queue/semaphore waits. Per-call timeouts cannot extend it.
  • Cost/tokens and lineage: account every provider/profile, with explicitly defined estimates where usage is absent. Provider-side billed spend may not be knowable exactly before a request.

Use canonical tool names and a single reservation path. Parallel calls must not each read the same remaining allowance and overspend it. Rejected calls still consume model/round effort; errors and empty results are not free retries.

B. Make exhaustion an explicit state

Proposed outcome vocabulary (not existing status values):
completed      requested work finished
exhausted      rounds / calls / repeats / deadline / cost cap reached
failed         known failure prevented completion
cancelled      operator or caller cancelled the operation
uncertain      an external side effect may have committed

Record: stop reason, admitted/completed calls, model attempts,
elapsed time, profile, origin and parent/child operation IDs.

Distinguish internal completion from delivery. A budget summary can be delivered successfully while the underlying task remains exhausted. A known successful send is not permission to send it again.

C. Reserve finalization inside the hard deadline

  • Allocate a work deadline before the overall deadline; keep a small explicit summary/delivery reserve.
  • When no more tools may run, do not request an ordinary tool-enabled continuation.
  • If valid native tool calls are already in history, append a result for every call ID, including calls not executed because of the budget. Preserve protocol coherence.
  • Disable execution, not only tool schemas. Text-call recovery, auto-search and HTML auto-routing must not revive tools during finalization.
  • If no summary request can fit, return a deterministic partial-work notice. Never exceed the hard deadline in order to explain that it expired.
  • For explicit silence or already-completed delivery, avoid unnecessary extra messages. For background work, do not convert exhaustion into “job done.”

D. Stop repeated work without breaking legitimate workflows

Keep a turn-scoped ledger outside trimmed prompt history. For read-only tools, compare normalized tool name and arguments; ignore transient fields such as reasoning/call IDs. Reuse an identical successful search result rather than querying again. Bound deliberate refresh/retry attempts separately.

For similar-but-not-identical queries, use a per-search cap and repeated-no-new-result strikes; do not rely only on string equality or a model's claim that it is making progress. Treat writes differently: repeated arguments can mean an intentional countdown or a dangerous duplicate. Require tool-specific delivery/idempotency semantics rather than blanket deduplication of all send_message, shell or posting calls.

E. Propagate policy through children and schedulers

  • Give every child an origin and parent ID. A detached job may outlive its interactive parent only through an explicit allowed extension.
  • Child permissions are the intersection of parent permissions and the child profile—not a fresh unrestricted catalog. Recheck current global, feature and plugin restrictions at child dispatch so a later disable still prevents new execution.
  • Set limits on child count, depth, concurrent children and aggregate lineage work. Admission should reserve from the parent/instance allowance rather than manufacture a fresh unlimited budget.
  • Recurring autonomy/plugin/inbox work needs per-tick limits plus aggregate rate/spend limits. Preserve existing platform authorization and X quotas.
  • Do not let a model extend its own allowance through configuration tools, delegation or a different call syntax.

F. Treat cancellation and external writes honestly

An async timeout requests cancellation; it neither guarantees immediate return nor proves underlying work stopped. In particular, asyncio.wait_for waits for cancellation cleanup, which can exceed its nominal timeout. The deadline must stop admission and bound user-facing waiting while a supervisor tracks cancellation-resistant workers separately. A DDGS thread, subprocess, Docker operation, SMTP send or remote social API can remain active or uncertain after the response deadline. Track owned tasks/workers, prevent new dispatch after cancellation, bound worker lifetimes, and reconcile uncertain writes. Retain occupied concurrent capacity until the worker actually settles; a cancelled UI status does not free a real worker. Keep the per-action confirmed/uncertain outcome even when the parent is cancelled or exhausted. Only refund consumed-work quota when an operation is known not to have consumed it. Retry a non-idempotent operation only with proof of noncommit or a supported idempotency key.

At the provider layer, recompute remaining time before every HTTP attempt and fallback, including after slot acquisition and backoff. At the tool layer, split the user-critical search result from optional RAG persistence under an explicitly bounded follow-on allowance. Avoid replacing one invisible wait with unowned background tasks.

Configuration contract to agree before implementation

  • Keep max_tool_iterations as a documented compatibility key for foreground rounds; do not silently reinterpret it as individual calls.
  • Add clearly named total-call, per-tool, deadline and profile controls. The names in this report describe a proposed contract, not copy-paste-ready configuration.

Lower foreground and background budgets separately and use feature switches if a tool must actually be disabled.
07 / Reviewable implementation slices

Land the brakes without replacing the engine

  1. Pin the failures with offline regression tests. Cover foreground batch counts/exhaustion, Telegram deadline parity, background terminal sends, deadline overshoot and parent-policy delegation.
  2. Fix completion semantics. Explicit terminal outcomes, exhausted status and a bounded tools-disabled wrap-up. Small patch; no unrelated architecture cleanup.
  3. Introduce the shared budget/reservation component. Cover initial calls, pre-tools, native/recovered calls, semaphore waits and retries. Wire Discord and Telegram to the same semantics.
  4. Integrate jobs and unattended paths. Child lineage, inherited permissions, finite tick allowances, plugin host contract and auxiliary provider accounting. Retain legitimate detached lifetimes.
  5. Make external writes safe. Separate retryable reads, definite failures and ambiguous commits for X/email/message/site/shell operations. Reconcile or report uncertainty instead of blind replay.
  6. Unify controls and documentation. Expose effective foreground/background profiles, zero semantics and stop reasons. Include deployment templates and the official multi-platform configuration contract.
  7. Validate and stage rollout. Narrow offline tests first, then the full offline suite with secrets/network excluded. Use mocked platform contract tests, then separately authorized sandbox-account acceptance before production.

Suggested ownership: orchestration owns reservation/deadline/outcome semantics; providers own attempt/deadline propagation; platform/tool owners own write idempotency and cancellation; API/dashboard owns effective configuration and diagnostics. One contract, multiple small commits.

Record aggregate counters rather than prompt bodies: operation ID, origin, profile, rounds, admitted calls by tool, provider attempts, elapsed time and stop reason. A useful progress display is “search 3/4 · tools 7/24 · time 65/180 s,” not an endlessly refreshed “working…” label. Redact queries and message content unless a separately approved diagnostic mode requires them.

Repair acceptance checklist

  • Batch reservation: a batch larger than the remaining allowance never executes more than admitted. Parallel calls cannot oversubscribe. Every native call ID receives a coherent executed/rejected result.
  • Cross-platform parity: parameterized Discord/Telegram tests enforce the same count/deadline contract; X/email/manual paths consume appropriate operation budgets without inventing model rounds.
  • Final round: native tool-only, text-recovered and mixed text/tool responses cannot dispatch after exhaustion or disappear without a defined terminal outcome.
  • Disabled/finalizing mode: zero tools means no auto-search, recovery dispatch, HTML auto-routing or child spawning. Explicit silence and already-delivered answers do not cause duplicate summaries.
  • Repeated work: identical successful searches, empty-result loops, altered reasoning fields, alternating queries and repeat attempts across trimmed history all stop as specified; legitimate stateful sequences still work.
  • Deadlines: test expiry during queue wait, semaphore wait, provider backoff/fallback, dispatch, RAG persistence and finalization. No new work starts after the deadline.
  • Terminal jobs: successful send_message/no_response with empty assistant content stops appropriately; acknowledgment-only and mixed batches follow the agreed semantics. Exhaustion/failure never becomes task success.
  • Delegation: autonomy cannot regain blocked research through a child. Test parent/child/grandchild allowances, maximum children, restart recovery and explicit detached extensions.
  • Side effects: a backend accepts a write then loses its response. No automatic second writer, quota refund or message replay until outcome is known. Test X posts, SMTP mixed accepted/refused recipients and cancellation while its worker continues, plus other non-idempotent tools.
  • Cancellation: stop while queued, generating, executing and delivering; track owned subprocess/thread/external work and report uncertain outcomes. No zombie model turn after user cancellation.
  • Recurring work and plugins: finite per-tick allowance, aggregate instance quota, no budget reset by event/job delegation; trusted plugin limitations explicitly tested/documented.
  • Configuration: test defaults/overrides/zero/invalid values and API/UI/runtime agreement. Display effective background values, not unexplained inheritance sentinels.
  • Fairness and regressions: one exhausted research task does not starve other channels, voice or administrative cancellation. Run existing progress, reply, provider-fallback and tool-contract suites.

Existing tests cover some numeric clamping, job admission/basic success and search formatting. They do not establish the aggregate budget/deadline/exhaustion contract above. See test inventory.

Decisions the team must make

  1. Approve foreground and background profile values and the semantics of every zero/unset value.
  2. Choose instance/lineage quotas, including whether privileged manual tasks may bypass a limit and who can approve that.
  3. Define intentional refresh/repeat policy per tool, especially delivery/stateful operations.
  4. Define cancel semantics for detached jobs versus their parent message, and recovery of in-flight work after restart.
  5. Choose outcome persistence and external-write reconciliation strategy before enabling automatic replay.
  6. Specify what telemetry can be retained without collecting message content or credentials.

Evidence boundary

Source inspection and focused mocked reproductions establish the local code paths and failures described here. They do not establish which paths the official deployment has exercised, what its effective limits are, or a particular production incident's exact cause. Before attributing a reported “endless run,” collect sanitized counters that distinguish one operation from multiple inbound events, new autonomy ticks or detached jobs.

The original audit did not read private environment files, stored messages, credentials, PM2 dumps or live service endpoints, and applied no runtime patch. Subsequent provider transport fixes are explicitly marked above; the broader shared operation-budget repair and proposed profile values remain team-review material.
